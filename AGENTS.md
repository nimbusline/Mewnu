# Mewnu: technical guide for coding agents

This file is shared project guidance. Keep personal machine settings, credentials, and calendar data out of the repository. Read `README.md`, `CONTRIBUTING.md`, and `RELEASING.md` for user-facing build, contribution, and release context.

## Product contract

- Mewnu is a read-only macOS 26+ menu bar view of the user's Apple Calendar data. It has no Dock window, account system, analytics, or network service.
- EventKit access is for reading events only. Never add event creation, edits, deletion, or storage of event content without an explicit product decision.
- Never log or commit real event titles, notes, locations, account names, or screenshots containing personal calendar data. Tests and screenshots use synthetic data.
- Keep German and English strings synchronized. Check keyboard navigation, VoiceOver labels, and the resizable menu window when changing UI.

## Source of truth and architecture

- `project.yml` defines the Xcode project. `Mewnu.xcodeproj` is generated by XcodeGen and checked in; run `scripts/generate-project.sh` after changing source files or project settings, and include the resulting project changes.
- `Mewnu/Core/CalendarService.swift` owns EventKit access. Its serial fetch queue converts mutable EventKit objects into `CalendarSnapshot` value models before returning to the main actor. Keep EventKit objects out of SwiftUI views and avoid parallel queries on the same store.
- `Mewnu/Core/CalendarViewModel.swift` owns permissions, month and day selection, filtering, refresh scheduling, and the hidden calendar IDs in `UserDefaults`. A revoked permission clears displayed data; a transient fetch failure retains the last successful data for the same month.
- `Mewnu/Core/CalendarMath.swift` builds the 42-day grid and indexes events by overlapping calendar days. Positive event ends are exclusive; timed zero-duration entries belong only to their start day. Reject negative intervals and zero-duration all-day entries. Use `Calendar` day boundaries rather than adding 86,400 seconds so daylight-saving changes work.
- `Mewnu/Core/EventDisplayText.swift` formats timed, overnight, multiday, and all-day event text. An all-day event's EventKit end date is exclusive; its displayed last day is inclusive.
- `Mewnu/Views/` contains the SwiftUI menu, month grid, agenda, filters, and detail view. Calendar colors are used for day markers; more than four calendars use three dots and an overflow count.
- `Mewnu/Core/MenuWindowSize.swift` stores the menu height in `UserDefaults` and clamps it to the available display height. The bottom grip in `ContentView` previews resizing and saves the final height.
- The app has no third-party runtime libraries. XcodeGen is a development and CI tool, not part of the distributed app.

## Verification

Use Xcode 27+ and XcodeGen 2.46.0 (pinned). Run focused tests for a change, then the relevant CI checks before considering it complete:

```sh
scripts/install-xcodegen.sh
scripts/validate-entitlements.sh
scripts/generate-project.sh
xcodebuild -project Mewnu.xcodeproj -scheme Mewnu -destination 'platform=macOS' \
  -enableCodeCoverage YES -resultBundlePath /tmp/MewnuUnitTests.xcresult \
  CODE_SIGN_IDENTITY=- CODE_SIGNING_ALLOWED=YES '-only-testing:MewnuTests' test
python3 scripts/check-unit-coverage.py /tmp/MewnuUnitTests.xcresult
xcodebuild -project Mewnu.xcodeproj -scheme Mewnu -destination 'platform=macOS' \
  CODE_SIGN_IDENTITY=- CODE_SIGNING_ALLOWED=YES '-only-testing:MewnuUITests' test
```

Use a fresh result-bundle path for each run. The coverage gate requires at least 95% line coverage **per listed core file**; it does not mean the entire app has 95% unit coverage. Unit tests use fake services, and UI tests use sample calendars. Before release, also check real EventKit permission changes, account synchronization, recurrence exceptions, all-day and overnight events, and large calendars on a test account.

## Release invariants

- `.github/workflows/ci.yml` runs unit tests, the coverage gate, a universal Release build, and UI tests. Keep the Release binary compatible with both `arm64` and `x86_64` and verify each slice with `lipo -verify_arch`.
- `.github/workflows/release.yml` and `scripts/release.sh` test, build, sign, notarize, and package the app. `project.yml`'s `MARKETING_VERSION` must match a release tag `vX.Y.Z`.
- Keep signing certificates, Apple account credentials, app-specific passwords, and real calendar data out of commits, test logs, and agent messages. Follow `RELEASING.md` for the release procedure.
- Do not call a release verified solely because a local build passes: signing, notarization, Gatekeeper assessment, and the GitHub CI result have separate checks.
